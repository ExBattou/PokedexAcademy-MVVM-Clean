De LiveData a Kotlin StateFlow y SharedFlow bajo Clean Architecture y Jetpack Compose

1. El Dilema del Estado Asíncrono en Android

En el desarrollo móvil con Android, la interfaz de usuario (UI) y las operaciones de fondo (red, base de datos) viven en mundos con ciclos de vida completamente desincronizados. La UI puede ser destruida y recreada en cualquier momento por el sistema operativo debido a eventos de configuración (el caso más clásico es la rotación de pantalla), cambios de idioma o muerte por baja memoria (Low Memory Killer).

Antes de 2017, las peticiones asíncronas se ejecutaban mediante Callbacks tradicionales o AsyncTask. Si la respuesta del servidor llegaba cuando la Activity ya había sido destruida por una rotación de pantalla, invocar cualquier método sobre la vista provocaba los infames NullPointerException: Attempt to invoke virtual method on a null object reference o provocaba fugas de memoria (Memory Leaks) al retener referencias vivas al contexto de la Activity destruida.

El Patrón Observer como solución fundamental
El Patrón Observer invierte el sentido de la comunicación. En lugar de que la vista solicite activamente los datos ("polling") o retenga callbacks directos, la vista se limita a suscribirse pasivamente a una fuente única de verdad inmutable (Single Source of Truth). Cuando los datos cambian, el observador es notificado automáticamente respetando su ciclo de vida.

2. Clean Architecture + MVVM: Separación de Responsabilidades

Para que una aplicación sea testeable y escalable, desacoplamos la lógica de negocio del framework de Android mediante Clean Architecture en tres capas estrictas:

  • Capa Data: Implementa los repositorios (PokemonRepositoryImpl) y Data Sources. Consume la API REST de PokeAPI mediante Retrofit y Moshi. Transforma los DTOs de red en modelos puros de dominio mediante PokemonMapper.
  • Capa Domain: El corazón del negocio. Es KOTLIN PURO. No conoce dependencias de Android, Retrofit ni Compose. Define los contratos de repositorio (interfaces) y los Casos de Uso (Use Cases) como GetGen1PokemonUseCase, GetGen2PokemonUseCase y GetPokemonDetailUseCase.
  • Capa Presentation: Contiene los ViewModels y la interfaz en Jetpack Compose. Los ViewModels orquestan la ejecución de casos de uso y exponen flujos observables a la pantalla.
⚠️ REGLA DE ORO ARQUITECTÓNICA
La capa domain NUNCA debe importar paquetes de androidx.lifecycle ni LiveData. LiveData y StateFlow son mecanismos de la capa de Presentación. El dominio solo debe manejar funciones suspendidas (suspend fun) o Flows puros de Kotlin.

3. El Enfoque Clásico: LiveData

Presentado en 2017 como parte de Android Architecture Components, LiveData es un contenedor de datos observable consciente del ciclo de vida (Lifecycle-aware).

Ciclo de Vida en LiveData

LiveData exige un LifecycleOwner (como una Activity, Fragment o Composable). Solo despacha actualizaciones si el componente se encuentra en un estado activo (STARTED o RESUMED). Si la app pasa a segundo plano (STOPPED), LiveData suspende las emisiones. Al destruirse la vista (DESTROYED), el observador se desuscribe automáticamente, eliminando de raíz las fugas de memoria.

Encapsulamiento con Backing Property

// 1. Estado mutable privado (solo el ViewModel puede modificarlo)
private val _uiState = MutableLiveData<UiState<List<Pokemon>>>(UiState.Idle)

// 2. Estado inmutable público (la vista solo puede OBSERVAR)
val uiState: LiveData<UiState<List<Pokemon>>> = _uiState

fun loadPokemon() {
    _uiState.value = UiState.Loading
    viewModelScope.launch {
        when (val result = getGen1PokemonUseCase()) {
            is Resource.Success -> _uiState.value = UiState.Success(result.data)
            is Resource.Error -> _uiState.value = UiState.Error(result.message)
        }
    }
}

Limitaciones de LiveData

  • Acoplamiento a Android: Vive en androidx.lifecycle. No se puede reutilizar en proyectos Kotlin Multiplatform (KMP).
  • Pobre catálogo de operadores: Solo cuenta con transformaciones básicas (map, switchMap). Carece de debounce, combine o buffer.
  • El bug de los Eventos One-Shot: LiveData retiene siempre el último valor. Si muestras un Snackbar o ejecutas una navegación, al girar la pantalla el nuevo observador vuelve a recibir el evento y se vuelve a disparar.

4. El Enfoque Moderno: Kotlin Flow (StateFlow y SharedFlow)

Kotlin Flow es un stream asíncrono y frío perteneciente a kotlinx.coroutines. Es agnóstico del sistema operativo y multiplataforma.

Cold Flows vs Hot Flows

  • Cold Flow (Frío): No produce datos hasta que alguien invoca collect(). Cada colector ejecuta el stream desde cero (ideal para queries a Room o llamadas a Retrofit).
  • Hot Flows (Calientes): Emiten datos continuamente aunque no haya nadie escuchando. Los dos flujos calientes por excelencia en Android son StateFlow y SharedFlow.

StateFlow: El Sucesor de LiveData para UiState

  • Valor inicial obligatorio: MutableStateFlow(UiState.Idle). El estado de la UI nunca es nulo ni indeterminado.
  • Replay = 1: Cualquier observador que se conecte recibe de inmediato el último estado disponible.
  • Conflación automática: Si se emite el mismo valor idéntico dos veces consecutivas (equals == true), StateFlow descarta la segunda emisión para evitar recomposiciones innecesarias.

SharedFlow: Eventos efímeros (One-Shot) sin hacks

Al configurarse con replay = 0 por defecto, un evento emitido por SharedFlow se consume y desaparece. Es la solución ideal para Snackbars, Toasts o triggers de navegación. 

// 1. Estado de pantalla (StateFlow)
private val _uiState = MutableStateFlow<UiState<List<Pokemon>>>(UiState.Idle)
val uiState: StateFlow<UiState<List<Pokemon>>> = _uiState.asStateFlow()

// 2. Canal de eventos one-shot (SharedFlow)
private val _effectFlow = MutableSharedFlow<Gen2UiEffect>()
val effectFlow: SharedFlow<Gen2UiEffect> = _effectFlow.asSharedFlow()

fun onFavoriteClick(pokemon: Pokemon) {
    viewModelScope.launch {
        _effectFlow.emit(Gen2UiEffect.ShowSnackbar("¡${pokemon.displayName} guardado!"))
    }
}

5. Consumo en Jetpack Compose

Para LiveData:

val uiState by viewModel.uiState.observeAsState(initial = UiState.Idle)

Para StateFlow:

val uiState by viewModel.uiState.collectAsStateWithLifecycle()
¿Por qué usar collectAsStateWithLifecycle() y NO collectAsState()?
collectAsState() mantiene activa la recolección aunque la aplicación pase a segundo plano, desperdiciando batería y ciclos de CPU. Por el contrario, collectAsStateWithLifecycle() cancela automáticamente la recolección si el ciclo de vida cae por debajo de Lifecycle.State.STARTED.

Para SharedFlow (Eventos con LaunchedEffect):

val snackbarHostState = remember { SnackbarHostState() }

LaunchedEffect(Unit) {
    viewModel.effectFlow.collectLatest { effect ->
        when (effect) {
            is Gen2UiEffect.ShowSnackbar -> snackbarHostState.showSnackbar(effect.message)
        }
    }
}

8. Anti-Patrones Críticos a Evitar

  1. Exponer Mutables públicos: Permite que la vista mute el estado del ViewModel externamente, destruyendo el encapsulamiento.
  2. Usar StateFlow para navegación: Provoca que al rotar la pantalla o presionar "Atrás", el evento de navegación vuelva a dispararse en bucle.
  3. Poner LiveData en Domain o Data: Acopla la lógica de negocio a Android e impide tests unitarios veloces sin emulador.
  4. Múltiples booleanos en lugar de Sealed Interface: Tener isLoading, isError y data por separado permite estados imposibles (ej: cargando y con error simultáneamente).
